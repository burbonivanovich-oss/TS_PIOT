# /cycle-listen — рутина B: слушатель редактора

Запускается по расписанию (каждые 4 часа по будням) в свежей сессии.
Это единственная точка, где человеческая обратная связь попадает в пайплайн.

**Главное правило: если нового нет — завершиться молча.** Рутина срабатывает
десятки раз в неделю; уведомление должно приходить только когда что-то
действительно произошло.

---

## Шаг 0 — Что сейчас

```bash
node scripts/cycle-state.mjs get --json
```

Развилка по `state`:

| Состояние | Что делать |
|---|---|
| `idle`, `done` | Выйти молча. Слушать нечего. |
| `awaiting_review` | Шаг 1 — комментарии в Issue плана |
| `approved` | Выйти молча. Ход за рутиной C. |
| `batch_review` | Шаг 2 — комментарии в PR батча |

---

## Шаг 1 — Ответ редактора по плану

Прочитать комментарии Issue `issueNumber` через `mcp__github__issue_read`
(method: `get_comments`).

**Отфильтровать:**
1. `id` > `lastSeenCommentId` — остальное уже разобрано.
2. Автор входит в `editorLogins`. Если список пуст — принимать любого,
   кроме ботов.
3. Отбросить свои же комментарии (автор — бот/тот же аккаунт, что открыл Issue).

Если после фильтра пусто — выйти молча, состояние не трогать.

### 1а. Классификация

По каждому новому комментарию, в порядке возрастания `id`:

| Класс | Признак | Действие |
|---|---|---|
| **Одобрение** | Текст начинается с `одобряю`, `одобрено`, `принято`, `утверждаю`, `го`, `поехали`, `approve`, `lgtm` | Шаг 1в |
| **Отклонение** | Начинается с `отклоняю`, `отменяю`, `стоп` | Шаг 1г |
| **Правки** | Всё остальное содержательное | Шаг 1б |
| **Шум** | Реакция, `+1`, пустой текст | Пропустить |

Если в одной пачке есть и правки, и одобрение — **сначала применить правки,
потом одобрить**. Порядок по `id`, не по важности.

### 1б. Применение правок

Распознаваемые формулировки (свободный текст, не команды — понимать по смыслу):

| Редактор пишет | Действие |
|---|---|
| `убрать 3, 7` / `сними тему про X` | `node scripts/cycle-state.mjs drop-topic <slug>` |
| `добавить: <тема>` | `node scripts/cycle-state.mjs add-topic --slug <транслит> --title "..." --priority P1 --cluster <кластер> --keyword "..."` |
| `4 → P0` / `подними приоритет у X` | Отредактировать `priority` темы в состоянии |
| `2: переформулировать на "..."` | Обновить `title` и `targetKeyword` темы |
| Вопрос по теме | Не менять план, ответить по существу |

Если формулировка непонятна — **не угадывать**. Ответить уточняющим вопросом
в ветке и не трогать план.

Для правок приоритета и формулировок, которых нет в CLI, редактировать
`src/data/editorial-cycle.json` точечно, сохраняя схему.

**Ответить в ветке** через `mcp__github__add_issue_comment`:

```markdown
Применил:

- снял тему 3 «[название]»
- добавил «[название]» (P1, кластер [x])
- тема 4 → P0

Обновлённый план — N тем (P0: n, P1: n, P2: n):

| # | Приоритет | Тема | Целевой запрос |
|---|---|---|---|

Одобрить — комментарием со словом «одобряю».
```

Состояние остаётся `awaiting_review`.

### 1в. Одобрение — план едет в репозиторий

Только здесь контент-план впервые меняется:

1. Записать все темы цикла в `src/content/wiki/content-plan-2026.md`
   в соответствующие кластерные разделы с пометкой
   `# [cycle-plan YYYY-MM-DD, одобрено редактором]`.
2. `node scripts/generate-editorial-plan.mjs` — пересобрать JSON.
3. `node scripts/cycle-state.mjs set-state approved`
4. Закоммитить: `cycle: план <YYYY-MM> одобрен редактором (#<issue>)`, запушить.
5. Снять с Issue метку `ждёт-редактора`, повесить `план-одобрен`.
6. Ответить в ветке:

```markdown
План принят, записал в контент-план.

Первый батч — 3 статьи с наивысшим приоритетом:
1. [название]
2. [название]
3. [название]

Соберу их ближайшим запуском и пришлю одним PR.
Следующий батч начнётся только после того, как закроете этот —
так правки не накапливаются.
```

### 1г. Отклонение

`node scripts/cycle-state.mjs reset --force`, закрыть Issue с комментарием,
что план пересоберётся в следующем цикле. Причину из комментария редактора
записать в `src/content/wiki/` заметкой, чтобы следующий план её учёл.

### 1д. Отметить прочитанное

```bash
node scripts/cycle-state.mjs seen-comment <максимальный обработанный id>
```

Закоммитить состояние. **Без этого шага рутина обработает те же
комментарии повторно.**

## Шаг 2 — Ответ редактора по батчу статей

Взять из состояния открытый батч (`batches[].state == "open"`), его `pr`.

### 2а. Проверить, не смержен ли PR

`mcp__github__pull_request_read` (method: `get`).

Если `merged == true`:

```bash
node scripts/cycle-state.mjs close-batch --pr <номер>
```

Закоммитить состояние. Прокомментировать в Issue плана:

```markdown
Батч N принят и влит (PR #X).
Осталось тем в цикле: M. Следующий батч соберу ближайшим запуском.
```

Если после `close-batch` состояние стало `done` — написать, что цикл закрыт,
и закрыть Issue плана.

Если PR закрыт без мержа — вернуть темы батча в `pending` правкой состояния
и сообщить редактору, что темы вернулись в очередь.

### 2б. Комментарии и ревью в PR

Собрать через `mcp__github__pull_request_read`:
- `get_comments` — обычные комментарии,
- `get_review_comments` — привязанные к строкам,
- `get_reviews` — вердикты ревью.

Фильтр тот же: новее `lastSeenCommentId`, автор-редактор, не свои.

Пусто — выйти молча.

По каждому замечанию:
1. Открыть файл статьи, внести правку.
2. Ответить в треде через `mcp__github__add_reply_to_pull_request_comment`
   с описанием, что изменилось. Одна правка — один ответ, без общей простыни.
3. Если замечание требует пересборки фактуры — прогнать `/factcheck <slug>`.
4. Если правка стилистическая — прогнать `node scripts/check-ai-markers.mjs`
   после неё.

Запушить правки в ветку батча. Итоговым комментарием:

```markdown
Правки внесены, N замечаний закрыто:
- [файл] — [что изменилось]

Проверки после правок: check-ai N/10, factcheck зелёный.
```

Состояние остаётся `batch_review`. Отметить `seen-comment`.

**Если правка спорная** — например, редактор просит убрать ссылку на НПА,
которая нужна по редполитике, — не спорить в треде молча и не выполнять
вслепую. Внести то, что бесспорно, и по спорному пункту задать вопрос
с объяснением, чем это грозит.

## Итоговый отчёт

Когда что-то сделано:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Рутина B — обработан ответ редактора

Цикл:        <id>          Состояние: <было> → <стало>
Комментариев: N
Применено:   [список]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

Когда пусто — вывести одну строку `Новых комментариев нет` и завершиться.

---

## Правила

- Нет нового — выходить молча, состояние не менять.
- Никогда не откатывать `lastSeenCommentId` назад.
- Не одобрять план за редактора и не мержить PR самому.
- Непонятную правку не угадывать — переспрашивать.
- Каждое изменение состояния коммитить и пушить сразу: следующая рутина
  читает его из репозитория, а не из памяти.
- Язык ответов — только русский.
