# /cycle-batch — рутина C: батч статей

Запускается по расписанию (понедельник, утро) в свежей сессии.
Пишет **3 статьи за раз**, не весь план.

Смысл ограничения: редактор проверяет 3 статьи за один подход и не тонет
в правках. Пока предыдущий батч висит на ревью, новый не начинается —
это жёсткий предохранитель, а не рекомендация.

---

## Шаг 0 — Предохранитель

```bash
node scripts/cycle-state.mjs can-start-batch
```

**Ненулевой код возврата — СТОП.** Вывести причину из скрипта и завершиться
молча. Причины и что они значат:

| Вывод | Что происходит |
|---|---|
| `план ещё не одобрен редактором` | Ждём рутину B |
| `батч N висит на ревью (PR #X)` | Редактор ещё не закрыл прошлый батч |
| `все темы цикла написаны` | Цикл выработан, ждём рутину A |
| `цикл в состоянии idle/done` | Активного цикла нет |

Никогда не обходить этот шаг и не запускать батч «раз уж сессия началась».

---

## Шаг 1 — Отобрать темы

```bash
node scripts/cycle-state.mjs next-batch --size 3
```

Возвращает JSON-массив тем со статусом `pending`, отсортированных
P0 → P1 → P2. Размер переопределяется `--size`, но по умолчанию 3 —
менять только если редактор сам попросил.

---

## Шаг 2 — Ветка

```bash
git fetch origin main
git checkout -B content/batch-<cycleId>-<N> origin/main
```

`<N>` — номер батча: `batches.length + 1` из состояния.

---

## Шаг 3 — Написать статьи

Для каждой темы последовательно выполнить `/create-article "<title>"` —
все девять стадий со шлюзами. Не сокращать пайплайн ради скорости.

**Обработка сбоев по одной статье:**

- Статья не прошла шлюз после 2 попыток — не блокировать остальные.
  Отложить её, пометить в состоянии `batchStatus: "pending"` (остаётся
  в очереди) и записать причину для отчёта.
- Если из 3 тем прошла хотя бы одна — батч всё равно уходит в PR.
- Если не прошла ни одна — PR не открывать, сообщить редактору в Issue
  плана, что батч не собрался и почему.

**Бюджет сессии.** Три полных прогона `/create-article` — это много.
Если видно, что сессия не дотянет, довести до конца текущую статью,
закоммитить готовое и открыть PR с тем, что есть. Незавершённые темы
остаются `pending` и попадут в следующий батч. Частичный батч лучше
оборванного.

---

## Шаг 4 — PR

Все статьи батча — **одним PR**, не тремя. Редактору так проще: один
подход, один тред.

```bash
git push -u origin content/batch-<cycleId>-<N>
```

`mcp__github__create_pull_request`:

**Заголовок:** `Батч N — <cycleId>: <k> статей`

**Тело:**

````markdown
Батч N по контент-плану <cycleId> (#<issue плана>).

## Статьи

### 1. [Заголовок]
`src/content/blog/<slug>.md` · [кластер] · P0 · **NNNN слов**
Целевой запрос: `[запрос]`
Оценка `/analyze-article`: **NN/100** · check-ai: **N/10** · factcheck: зелёный

[2–3 предложения: о чём статья и на что смотреть при вычитке]

<!-- по одному блоку на статью -->

## Что проверено автоматически

| Проверка | Результат |
|---|---|
| NPA-аудит (`audit-npa-references.mjs --strict`) | зелёный |
| Factcheck | нет claims с confidence < 0.7 |
| check-ai маркеры | N/10 (порог 6) |
| Редполитика Контура | «вы» строчной, без канцеляризмов, активный залог |
| Перелинковка | ≥ 3 внутренних на статью, сироты отсутствуют |
| ПРОМО-маркеры | по 3 на статью |

## Что нужно от вас

Вычитайте статьи и оставьте замечания комментариями к строкам —
я разберу их в течение 4 часов и отвечу в тредах.

Когда всё устроит — влейте PR. Следующий батч начнётся только после этого.

Осталось тем в цикле после этого батча: **M**.
````

Если какие-то темы отложены — отдельный раздел:

```markdown
## Не вошли в батч

- «[тема]» — [причина: не прошла шлюз factcheck / не хватило бюджета].
  Остаётся в очереди, войдёт в следующий батч.
```

## Шаг 5 — Зафиксировать состояние

```bash
node scripts/cycle-state.mjs add-batch \
  --slugs <slug1,slug2,slug3> \
  --pr <номер PR> \
  --branch content/batch-<cycleId>-<N>
```

В `--slugs` перечислять **только реально написанные** статьи.
Скрипт переведёт цикл в `batch_review` и не даст стартовать следующему батчу.

Закоммитить состояние в `main`:

```bash
git checkout main
git add src/data/editorial-cycle.json
git commit -m "cycle: батч N отправлен на ревью (PR #<номер>)"
git push -u origin main
```

Состояние коммитится в `main`, а не в ветку батча: иначе следующая рутина
прочитает устаревшее состояние и запустит батч поверх открытого.

## Правила

- `can-start-batch` не обходить никогда.
- 3 статьи по умолчанию, не больше.
- Один PR на батч.
- Статьи уходят с `draft: true` — публикацию делает `/release-article`
  после мержа.
- Сбой одной статьи не отменяет батч.
- Состояние коммитить в `main`.
- Язык — только русский.
