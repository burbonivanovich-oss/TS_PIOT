# /cycle-plan — рутина A: план на согласование

Запускается по расписанию (1-е число месяца) в свежей сессии.
Результат — GitHub Issue с планом и уведомление редактору.

**Ключевое правило: `content-plan-2026.md` на этой стадии не изменяется.**
План живёт в состоянии цикла и в теле Issue. В репозиторий он попадёт
только после одобрения редактором — это делает рутина B.

---

## Шаг 0 — Проверка, что цикл свободен

```bash
node scripts/cycle-state.mjs get
```

Если состояние **не** `idle` и не `done` — СТОП. Вывести:

```
Цикл <id> уже идёт (<состояние>). Новый план не создаю.
Issue: #<номер>
```

Ничего не делать и завершиться. Два открытых плана одновременно — гарантия
путаницы у редактора.

---

## Шаг 1 — Сбор тем

1. Прогнать `/monitor-rss` — новости за 30 дней.
2. Прогнать `/cluster-gaps` — пробелы по всем 18 кластерам.
3. Прочитать `src/data/editorial-plan.json` — отсеять всё, что уже
   `status: "done"` или уже `planned`.
4. Прочитать `src/data/wordstat/keys.json` — частотности для приоритизации.

Приоритеты — по правилам из `/plan-content` (шаг 3):

| Приоритет | Критерий |
|---|---|
| **P0** | Дедлайн ≤ 90 дней ИЛИ активная новость + пробел в кластере |
| **P1** | Спрос 500–2000 без покрытия ИЛИ тренд в источниках |
| **P2** | Полезная тема, нет срочности |

**Объём плана — 12 тем по умолчанию** (`--topics` переопределяет).
Не больше 4 P0 на цикл: если P0 больше, лишние понижаются до P1 с пометкой
в обосновании. Цикл из 12 тем при батче в 3 статьи — это 4 подхода редактора.

---

## Шаг 2 — Файл плана

Сохранить темы во временный JSON (он нужен только для `cycle-state.mjs init`):

```json
[
  {
    "slug": "ts-piot-shtraf-2026",
    "title": "Штраф за работу без ТС ПИоТ в 2026 году",
    "priority": "P0",
    "cluster": "ts-piot",
    "targetKeyword": "штраф за работу без тс пиот",
    "rationale": "Дедлайн 01.07.2026, спрос 2400/мес, в кластере нет статьи"
  }
]
```

Путь — во временную директорию, не в репозиторий.

## Шаг 3 — Issue редактору

Создать Issue через `mcp__github__issue_write` в `burbonivanovich-oss/TS_PIOT`.

**Заголовок:** `Контент-план <YYYY-MM> — на согласование`

**Метки:** `контент-план`, `ждёт-редактора`

**Тело:**

````markdown
## Контент-план на <месяц прописью YYYY>

Собран автоматически <DD.MM.YYYY>. Источники: RSS за 30 дней,
пробелы кластеров, частотность Wordstat.

Тем в плане: **N** (P0: n, P1: n, P2: n).
Писаться будут батчами по 3 статьи — не всё сразу.

### Темы

| # | Приоритет | Тема | Целевой запрос | Кластер | Обоснование |
|---|---|---|---|---|---|
| 1 | P0 | [название] | `[запрос]` | ts-piot | [почему сейчас] |

---

## Что от вас нужно

Один из трёх вариантов — просто напишите комментарием:

**1. Одобрить целиком.** Комментарий начинается со слова `одобряю`
   (или `принято`, `утверждаю`, `го`). После этого я записываю план
   в репозиторий и начинаю писать первый батч из 3 статей.

**2. Одобрить с правками.** Напишите, что поменять — свободным текстом.
   Понимаю формулировки вида:
   - `убрать 3, 7` — снять темы по номерам из таблицы
   - `добавить: как выбрать ОФД для общепита` — новая тема в план
   - `4 → P0` — поменять приоритет
   - `2: переформулировать на "маркировка воды с 01.09.2026"`
   Отвечу в этой же ветке списком того, что применил, и обновлю таблицу.
   Одобрение — отдельным комментарием, когда всё устроит.

**3. Отклонить.** Комментарий со словом `отклоняю` + причина.
   Цикл закрывается, план пересобирается в следующем запуске.

Проверяю эту ветку каждые 4 часа по будням.
````

---

## Шаг 4 — Зафиксировать состояние

```bash
node scripts/cycle-state.mjs init \
  --cycle <YYYY-MM> \
  --issue <номер созданного Issue> \
  --plan <путь к временному JSON> \
  --editors <github-логин редактора> \
  --batch-size 3
```

Закоммитить и запушить состояние:

```bash
git add src/data/editorial-cycle.json
git commit -m "cycle: план <YYYY-MM> отправлен редактору (#<issue>)"
git push -u origin <ветка>
```

Состояние обязано попасть в репозиторий: следующая рутина запустится
в другой сессии и прочитает его оттуда.

## Правила

- Контент-план в репозитории не трогать — только после одобрения.
- Не создавать второй Issue, если цикл уже идёт.
- Не больше 4 P0 на цикл.
- Язык Issue — только русский.
- Не запускать `/create-article` — это работа рутины C.
