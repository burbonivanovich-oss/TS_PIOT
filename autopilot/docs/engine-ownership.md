# Где править и запускать Автопилот

Обновлено 7 октября 2026 года, AUD-09. Движок является частью репозитория сайта TS_PIOT: `autopilot/`, контент и состояние доставляются одним Git-деревом. Локальная копия с именем TS_PIOT сама по себе не означает действующий production-runner.

## Роли рабочих копий

Базовый каталог этой установки: `/Users/artemporubov/Documents/Pet projects`.

| Копия | Роль | Правило работы |
|---|---|---|
| `TS_PIOT-autopilot-runner` | Единственный ежедневный runner на `main` | Запускает `daily.mjs`; источник рабочего состояния, нарядов и очереди |
| `TS_PIOT-audit-20261007` | Изолированная разработка, ветка `codex/audit-facts-2026-10-07` | Изменения и проверки; её состояние не переносится в runner целиком |
| `TS_PIOT` | Исходный checkout с незавершённой работой | Не сбрасывать, не переключать ветку и не заменять файлы ради рутины |
| `Etiketka` | Песочница движка без remote; бэклог и доказательства | Её тесты и счётчики не описывают production; запуск мутаций с рабочим CONTENT_ROOT запрещён |

Дата и HEAD инвентаря — наблюдение, а не вечный выбор версии. Перед переносом повторно проверить HEAD, грязные файлы, живого владельца lock и незавершённую доставку. В разработке и runner есть `guard.mjs`, `site.mjs`, общий lock и отдельные бюджеты; в песочнице этих защит недостаточно. Слепое копирование каталогов может удалить защиты.

## Нормы и открытое требование 200

Предоставленные инструкции Etiketka требуют 200 статей в месяц. Это требование сохраняется и не объявляется достигнутым. Фактически установленный контракт runner — 55 NEW и 14 REWRITE в месяц, один проход в день, не более 3 за проход, 4 активных слота, обычный запас 14. Его единственный источник чисел — `autopilot/config/autopilot.config.json`. Срочные подтверждённые исправления могут превысить запас, но не месячный бюджет и дневной календарь.

Расхождение 200 и 55/14 описано явно; этот документ не меняет конфиг или предоставленные требования. Переход к 200 — отдельная работа: определить состав NEW/REWRITE, проверить модельную ёмкость, стоимость, число слотов выпуска, фактическое качество корпуса и ресурс восстановления. При потолке 3/сутки календарь физически допускает лишь 84–93 суммарных события за 28–31 день. Менять норму без соответствующей ёмкости нельзя.

## Один владелец исполнения

В сохранённой локальной конфигурации действует `automation-2`, «Этикетка — ежедневный выпуск», ежедневно в 09:00. Её prompt указывает именно на `TS_PIOT-autopilot-runner` и [auto-day](../../.agents/skills/auto-day/SKILL.md). Сохранённое расписание не доказывает будущий запуск: результат читается из journal/runs и публичных квитанций.

В корневом `.github/workflows/autopilot.yml` активного cron нет: workflow остаётся ручным диагностическим/служебным путём. `.github/workflows/auto-publish.yml` только читает очередь. Ручные plan/settle не запускаются поверх ежедневного владельца. Деплой сайта — `.github/workflows/deploy-gh-pages.yml`; это отдельный этап доставки, не второй писатель контента. Новое расписание при переносе кода не создаётся.

## Безопасная диагностика действующего runner

Команды выполнять из корня `TS_PIOT-autopilot-runner`, не из Etiketka:

```bash
pwd
git status --short
git rev-parse HEAD
node autopilot/scripts/state.mjs get --json
node autopilot/scripts/run.mjs latest --json
node autopilot/scripts/health-check.mjs --json
node autopilot/scripts/metrics.mjs --json
```

Здесь `state get`, `run latest`, `health` и `metrics` — чтение. Не добавлять plan/settle, refill, source refresh, unlock, reconcile или build к диагностике без оценки их записи и владельца. Отсутствие lock-файла само по себе не доказывает остановку scheduler.

На macOS `core.precomposeUnicode` может показывать уже отслеживаемый PDF как untracked из-за различия Unicode-нормализации имени. Сначала сопоставить Git blob и байты файла; не удалять файл ради чистоты. Подтверждённый случай диагностируется командой `git -c core.precomposeUnicode=false status --porcelain --untracked-files=all`; для вложенных Git-команд нужен такой же процессный override, без изменения глобального конфига. Реальная грязная работа по-прежнему блокирует перенос.

## Перенос изменений

1. Работать в изолированной ветке. Менять код, конфиг и доказательства адресно; весь каталог `data/` не копировать. Не заменять рабочие orders, journal, publish-log и счётчики снимком разработки.
2. Выполнить подходящие положительные и отрицательные проверки. Для кода движка — полный набор `npm test` из `autopilot/`; для контента — полные гейты и сборка; для документации — проверка содержания и локальных ссылок. Последующие узкие изменения проверять по их риску.
3. Убедиться, что runner на ожидаемой чистой `main`, прежняя доставка терминальна, живого владельца нет. Захватить штатный общий lock на всё время переноса; проверку HEAD и дерева повторить уже внутри lock.
4. Перенести конкретные проверенные коммиты cherry-pick. Сверить operational data до/после и выполнить необходимые проверки установленной версии. При конфликте остановить перенос, сохранив работы; не применять сброс или force-push.
5. Перед push сверить remote HEAD с исходным ожидаемым. Обычный push и повторное чтение remote подтверждают доставку коммита, а не публикацию.
6. Для изменений публичного результата дождаться деплоя, проверить `release.json` и затронутые страницы по [правилам проверки сайта](live-release.md). SHA отправленного дерева может отличаться от content/metadata SHA. Точное HTML-сравнение требует production-флага `PUBLIC_COMMERCIAL_EVENTS_ENABLED=true` и детерминированной сборки.

Полный ежедневный проход и восстановление выполняются командой из [auto-day](../../.agents/skills/auto-day/SKILL.md); процедуры остановки — в [runbook](runbook.md). Старые альтернативные клоны и тестовые корпуса не назначаются исполнителями и не удаляются этой процедурой.
