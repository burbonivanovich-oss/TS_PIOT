Дата аудита: 2026-09-13.

Назначение: этот файл целиком передаётся другой нейросети как самостоятельное
задание. Контекст предыдущего диалога ей не нужен. Агент должен работать из
корня репозитория `Etiketka`, читать `AGENTS.md` как главный источник правил и
исполнять задачи ниже строго по зависимостям.

Статус документа: исполнительный бэклог до первого промышленного запуска. Он
основан на текущем checkout `Etiketka`; репозиторий принимающего сайта TS_PIOT
и существующий сервер в аудит не входили, потому что недоступны. Все пункты,
которые требуют их проверки, отмечены `BLOCKED`.

## Задание агенту

Твоя цель — довести автономный контент-контур до состояния, в котором его
можно безопасно подключить к настоящему TS_PIOT и запустить на существующем
сервере, не затронув другие размещённые там проекты.

Работай последовательно до тех пор, пока не будут закрыты все доступные
карточки либо дальнейшее продвижение действительно потребует внешнего доступа
или решения владельца. Не останавливайся после одного анализа или первой
зелёной проверки.

Не ограничивайся написанием рекомендаций. Для каждой доступной задачи:

1. исследуй реальный код и текущее состояние;
2. внеси минимально достаточное изменение;
3. добавь позитивные и негативные тесты;
4. запусти проверки;
5. изучи получившийся diff;
6. обнови статус задачи и приложи evidence;
7. переходи к следующей разблокированной задаче.

Не объявляй весь проект готовым, пока не пройдены целевые ворота выпуска из
этого документа. Зелёный `npm test` сам по себе не является готовностью.

## Непереговорные правила исполнения

- Не удаляй, не сбрасывай, не stash'ь и не перезаписывай существующие
  пользовательские изменения.
- Перед первой правкой выполни `git status --short`, изучи `git diff` и отдели
  свои изменения от уже существовавших.
- Не запускай `plan`, `settle`, `interlink apply`, `dedupe scan` и другие
  мутирующие команды на реальном корпусе до выполнения соответствующих P0.
- Для экспериментов используй временный fixture/sandbox, а не production
  content tree.
- Не создавай пустой `src/content/blog`, чтобы искусственно сделать
  health-check зелёным.
- Не ослабляй редакционные пороги ради прохождения теста или конкретной
  статьи.
- Не редактируй `data/*.json` руками. Миграции состояния реализуй отдельным
  идемпотентным скриптом с dry-run, backup и тестами.
- Любая ошибка чтения корпуса, конфига или состояния должна завершаться
  fail-closed до записи файлов.
- Не включай расписание и не выполняй server mutation без фактических данных
  о хосте, доступов, backup и явной авторизации владельца.
- Не коммить и не push'ь без отдельного прямого разрешения. Подготовить diff,
  команды и отчёт можно без такого разрешения.
- Не добавляй runtime-зависимости без доказательства, что задачу нельзя
  надёжно решить стандартной библиотекой Node.js. Проект обязан работать на
  Node.js >=20 без установки dependencies.
- Не считай задачу закрытой, если проверен только happy path. Выполни все
  негативные случаи, перечисленные в карточке.
- Если обнаружена новая проблема того же или более высокого риска, добавь её
  отдельной карточкой с ID, зависимостями и критериями приёмки. Не прячь её в
  примечании.

## Границы полномочий агента

Агент может без дополнительного согласования:

- читать весь текущий репозиторий и доступный TS_PIOT;
- создавать и изменять код, тесты и документацию внутри выделенной рабочей
  копии;
- создавать временные fixtures;
- запускать локальные тесты, lint, dry-run и read-only диагностику;
- готовить deployment-файлы, runbook и команды для сервера.

Агент обязан остановиться и запросить конкретный недостающий ввод, если нужен:

- URL или credential репозитория TS_PIOT;
- SSH-доступ либо фактический inventory сервера;
- выбор между реально различающимися production-архитектурами после
  исследования;
- изменение DNS, nginx, systemd, cron, GitHub secrets или production branch;
- push, merge, удаление URL/статей или иное внешнее необратимое действие.

Запрос должен быть точечным: перечисли, что уже проверено, какой ровно факт
отсутствует, какую одну следующую операцию он блокирует и какой безопасный
вариант предлагается по умолчанию.

## Алгоритм выбора следующей задачи

1. Выбери карточку с наименьшим приоритетом по числу: P0 раньше P1, P1 раньше
   P2, P2 раньше P3.
2. Среди одного приоритета бери задачу, у которой выполнены все зависимости.
3. `CONFIRMED` означает, что дефект уже найден и задачу можно реализовывать.
4. `TODO` означает, что сначала нужно подтвердить предпосылку кодом/тестом, а
   затем реализовать.
5. `IN_PROGRESS` означает, что часть реализации есть, но хотя бы один критерий
   приёмки не выполнен; продолжай с незакрытого критерия.
6. `REJECTED BY REVIEW` означает, что реализация не прошла независимую
   негативную проверку; это активная задача с приоритетом выше обычного
   `CONFIRMED`.
7. `DECISION` не означает автоматическую остановку: сначала собери доказательства
   и выбери указанный безопасный default. Запрашивай пользователя только если
   выбор реально меняет production-архитектуру или требует новых полномочий.
8. `BLOCKED` не пытайся закрыть фиктивными данными. Продолжи с другими
   разблокированными задачами того же приоритета.
9. После реализации меняй статус карточки на `DONE` только вместе с evidence.

## Формат evidence в закрытой карточке

Добавляй под карточкой короткий блок следующего вида:

```text
Результат: DONE
Изменено: <файлы и краткая суть>
Положительная проверка: <команда> -> <точный результат>
Негативная проверка: <команда/fixture> -> <ожидаемый отказ>
Diff review: <что просмотрено, неожиданных изменений нет/перечень>
Остаточный риск: <нет или конкретный риск>
Commit: не создавался | <sha>
```

Не вставляй огромные логи. Указывай точные числа тестов, exit code и путь к
артефакту, если он создаётся.

## Формат отчёта агенту-владельцу после рабочего прохода

Каждый ответ начинай с результата, а не с плана. Используй ровно четыре
раздела:

1. `Завершено` — ID закрытых карточек и что реально изменилось.
2. `Проверено` — команды, результаты, негативные cases и diff review.
3. `Заблокировано` — только настоящие внешние блокеры с точным запросом.
4. `Следующий шаг` — один следующий разблокированный ID.

Не называй `BLOCKED` то, что просто трудно или требует дополнительного
исследования в доступном коде.

## Как читать приоритеты

| Приоритет | Значение | Правило запуска |
|---|---|---|
| P0 | Возможна публикация брака, потеря состояния или вмешательство в другой проект | Прод запрещён до закрытия |
| P1 | Контур работает, но метрики, качество или восстановление ненадёжны | Закрыть до наращивания темпа |
| P2 | Эксплуатационная зрелость и снижение ручной диагностики | Закрывать после безопасного canary |
| P3 | Оптимизация и расширение | Только после подтверждения ценности на реальном корпусе |

Оценки `S/M/L` — относительные: до половины дня, 1–2 дня, 3–5 дней. Они не
включают ожидание доступов и внешних решений.

## Целевые ворота выпуска

Продакшен-развёртывание допускается только когда одновременно выполнено:

1. Есть ровно один активный исполнитель и один источник состояния.
2. Любая недоступность или повреждение корпуса/JSON останавливает проход.
3. `plan`, написание, `settle`, build принимающего сайта и push образуют
   наблюдаемую цепочку с одним `runId`.
4. Забракованный материал физически не может быть опубликован соседним
   `auto-publish`.
5. Проверен откат состояния и контента из резервной копии/коммита.
6. На сервере процесс изолирован от остальных проектов пользователем,
   каталогами, блокировкой и лимитами ресурсов.
7. Пройден canary минимум на двух полных проходах без ручной правки данных.

## Стоп-условия

Любое из условий останавливает все мутирующие проходы:

- отсутствует/изменился маркер или Git remote принимающего проекта;
- JSON состояния не читается или инварианты очереди расходятся;
- уже работает другой scheduler/lock owner;
- забракованный held-материал выбирается публикатором;
- production build не проходит;
- push частично завершён или HEAD изменился конкурентно;
- нет проверенной резервной копии перед миграцией;
- service user видит каталоги чужого проекта на запись;
- три прохода подряд не достигают минимального результата по одной системной
  причине.

## Definition of Done для любого пункта

Пункт нельзя закрыть только по коду или зелёному exit status. Для `Done`
нужны: реализация, положительный тест, заявленные негативные тесты, отсутствие
неожиданного diff, обновлённая эксплуатационная документация и evidence
команды/артефакта. Для серверных пунктов дополнительно нужны фактический вывод
с целевого хоста и подтверждённый rollback.
