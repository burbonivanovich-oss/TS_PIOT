# Доставка прохода через Git

Исполнитель работает только в отдельном checkout, чистом до планирования. Начальная точка: `node autopilot/scripts/git-delivery.mjs begin`. После фактической приёмки и сборки: `node autopilot/scripts/git-delivery.mjs commit`. CLI выполняет preflight/тесты и удерживает общий lock. В текущем общем checkout guard и незакоммиченные изменения не обходятся.

Адаптер проверяет ветку/исходный HEAD, неизменность корпуса после сборки, допустимые файлы, симлинки, секреты и пустой пользовательский индекс. Повторная финальная сборка обязательна до создания content commit. Статьи, иллюстрации, подтверждения, публичная фактура и состояние идут через отдельный индекс. Первый commit содержит контент и состояние; второй добавляет в манифест SHA первого. Оба становятся видимыми в ветке одним compare-and-swap `update-ref`. Это одна атомарная смена ветки, а не последовательная публикация двух промежуточных состояний.

Durable журнал живёт в Git metadata, вне коммитируемого корпуса. До смены ветки сбой оставляет подготовленные объекты и допускает повтор; изменения файлов после подготовки блокируют смену ветки. После смены ветки повтор восстанавливает обычный индекс и не создаёт новых коммитов. При завершении следующая исходная точка архивирует журнал предыдущего прохода. Стадия committed доказывает существование Git-объекта контента; доставка в ветку подтверждается metadataCommit и чистым read-back.

Публичный `autopilot/research/<slug>.md` должен содержать проверенную фактуру и ссылки на источники. Он теперь доступен Git; остальные research-файлы, вложенные каталоги, chats и диагностические транскрипты остаются игнорируемыми. Артефакты доставки не могут использовать fixture-маркер для отключения скана секретов.

Интеграция: `node autopilot/scripts/daily.mjs --commit` записывает чистую исходную точку до source-monitor/plan и доставляет результат после settle. Prepared/content journal возобновляется до новой работы, даже если локальный манифест уже содержит committed. Без `--commit` такой журнал возвращает git_delivery_pending.

Пустой проход может сохранить только состояние: gated.published=0, корпус совпадает с исходным, изменены только файлы dataDir. В этом случае built не выставляется и сборка не выдумывается. Иллюстрации, фактура вне состояния и любые изменения корпуса требуют настоящей успешной сборки.

Границы: push, deployment и live-read-back ещё не реализованы; весь путь daily с настоящей моделью и Git в production-кандидате ещё не проверен. Изолированные модельные canaries начались со снимка незакоммиченных файлов, поэтому не имеют чистой исходной точки и не являются кандидатом на общий commit/push.
