# Коммерческая воронка: события и границы доказательства

Локальная реализация 03.10.2026. Цели добавлены в декларативный список `src/data/metrika/goals.json`; синхронизация с кабинетом не выполнялась. Приём событий в рабочем счётчике не доказан.

Новые события выключены по умолчанию. После сохранения семи целей счётчика 109130279 включить `PUBLIC_COMMERCIAL_EVENTS_ENABLED=true` в окружении сборки и проверить доставку на рабочем сайте. Сборка без этого явного значения не отправляет новые коммерческие события. Проверки на localhost остаются отключены даже с флагом.

| Событие | Что показывает | Чего не доказывает |
|---|---|---|
| product-view | Открытие страницы продукта | Просмотр всех блоков или покупку |
| product-cta-click | Клик на подключение: lead или external | Оплату по внешней ссылке |
| selector-task | Выбранную задачу | Пригодность решения |
| selector-result | Полученный результат, роль/форму бизнеса | Принятую заявку |
| selector-product-click | Переход из подбора к продукту | Подключение |
| form-start | Фокус на поле формы | Заполнение всех полей |
| form-submit-attempt | Событие submit | Успешный приём сервером или оплаченный заказ |

Ранее виджет отправлял `lead-*` на submit. Этот сигнал не был подтверждённым лидом. Новый код не отправляет его, а фиксирует form-submit-attempt. Исторические goal id оставлены в декларации и помечены пояснением; старые и новые периоды нельзя объединять под метрикой успешных лидов.

Параметры ограничены известными id офферов, задачами, ролями, формой бизнеса и типом перехода. Значения полей, телефон, email, ИНН, текст статьи, URL и query не передаются. Ошибка счётчика не должна блокировать подбор или переход. Для localhost/127.0.0.1/IPv6 loopback новые события отключены, чтобы проверки не создавали рабочую статистику.

Подтверждённый лид требует документированного сигнала успешного приёма от виджета или сверки партнёрского кабинета. Оплата и выплата — данные кабинета, не клики. До появления таких данных коммерческий отчёт должен показывать отсутствие подтверждения, а не нулевую/успешную конверсию.

Следующая приёмка COM-05: проверить реальные цели счётчика, рабочую доставку после деплоя, разрешённый сигнал успеха виджета, экспорт с одинаковым периодом и атрибуцией, базовый уровень конверсии и эксперимент. Форма не отправлялась при локальной проверке.


4 октября: семь JS-целей созданы существующим GitHub workflow и прочитаны обратно в счётчике 109130279. Коммерческие события включаются в production-сборке через PUBLIC_COMMERCIAL_EVENTS_ENABLED=true. Отправка попытки формы по-прежнему не подтверждает лид, оплату или выплату. Две прежние цели глубины/времени исправлены на API depth/visit_duration; истории существующих целей не удаляются.


## Коммерческий отчёт и экономика

`node autopilot/scripts/commercial-report.mjs --days 7 --json` строит окно из ровно семи календарных дат включительно, в UTC. Данные текущего дня являются срезом на указанное `asOf`, а не обещанием итогов за полный день.

Частные выгрузки хранить вне репозитория, задав `AUTOPILOT_COMMERCIAL_DATA_DIR=/absolute/private/directory`. Каталоги `partner`, `costs`, `receipts` внутри штатного data также исключены из Git. Исходные выгрузки с персональными данными или финансовыми реквизитами не добавлять в коммиты и PR.

Каждый источник содержит `fetchedAt` (ISO timestamp с часовым поясом) и `period: {from, to, timeZone: "UTC"}`. Период должен точно совпасть с запросом; фактическая выгрузка должна быть не старше 36 часов и не датирована будущим. Копирование файла не обновляет дату данных. При нескольких аналитических файлах выбирается свежая fetchedAt в запрошенном периоде.

В `analytics/*.json` поля `users`, `offerImpressions`, `productViews`, `formStarts`, `paymentClicks` — неотрицательные целые числа. CTR находится в диапазоне 0–1. `validLeads` принимается только при `confirmation.validLeads` с `source` равным `server-accepted` или `partner-cabinet`, относительным `evidenceRef` и `sha256` сохранённой первичной квитанции. То же правило действует в разрезах по офферу и источнику. События `form-submit-attempt` нельзя переименовывать в validLeads.

Конверсия требует `measurement.<metric>: {unit, cohort, unique: true, complete: true}` у обоих показателей и общий `asOf`. У числителя нужен `subsetOf`, явно содержащий ключ знаменателя: одинаковая аудитория сама по себе не доказывает прохождение предыдущего шага. Допустимы одинаковые уникальные единицы visitors, visits или leads, одинаковые период, аудитория и момент среза; complete означает полную выгрузку наблюдений среза, без выборки и обрезанных строк. Сырые события на посетителя не являются конверсией. Числитель больше знаменателя, отсутствие общего момента среза или несовпадение когорты дают «нет данных».

`partner/attribution.json` дополнительно требует `currency: "RUB"` и `verification: {source: "partner-cabinet", verifiedAt, evidenceRef, sha256}`. EvidenceRef — безопасный относительный путь внутри частного каталога данных; файл первичной выгрузки должен существовать, быть непустым и совпадать с SHA-256. Сверка чисел с первичным отчётом выполняется по реальным данным; метаданные и хеш сами по себе не доказывают достоверность записи партнёра. Счётные поля — целые, денежные — рубли с максимум двумя знаками после запятой.

`paid`/`paidCount` означают оплаченные клиентами счета партнёру. `commission` — начисленная комиссия Этикетки; `payout` — фактически выплаченные проекту деньги. Они выводятся отдельно. Поле JSON `revenue` оставлено для совместимости, но теперь равно projectIncome/commission, а не paid. При отсутствии комиссии доход остаётся неизвестным, даже если оплаты клиентов известны.

`costs/reconciliation.json` содержит такую же дату, период, валюту и первичную квитанцию, но `verification.source: "project-costs"`, `complete: true`, `totalCosts` и `asOf`. Итог netResult считается как комиссия минус сверенные полные затраты только при одинаковом периоде и моменте среза; это результат по начислению, а не денежный поток. Частичные затраты не доказывают прибыль. Отсутствующие данные остаются null/no-data/unverified; подтверждённый ноль остаётся числом 0.

Первичные данные партнёра ещё не собраны: эти проверки готовят корректный отчёт и не подтверждают реальные лиды, оплаты, комиссию или окупаемость.


## Ежедневное чтение коммерческих целей

`.github/workflows/commercial-analytics.yml` читает только счётчик Этикетки 109130279 каждый день в 06:00 UTC и при изменении своего коллектора. Семь action-целей ищутся по точному идентификатору; отсутствующие или неоднозначные цели не подменяются другими. Скрипт не отправляет события, формы или заявки, не пишет статьи и не делает коммиты.

`scripts/analytics/fetch-commercial.mjs` получает общие totals и уникальных целевых посетителей одним отчётом Метрики, с timezone=+00:00 и единым ограничением времени начала визита. Возвращённые query, порядок метрик, точность, округление, скрытые данные и data_lag проверяются. Числа из строк отдельных страниц не складываются. Достижения новых целей не становятся validLeads или paymentClicks.

Артефакт `metrika-commercial-7-days` хранится в GitHub три дня. В нём только агрегаты и служебные параметры запроса; OAuth и поля форм не сохраняются. Для локального коммерческого отчёта положить его `analytics/export.json` в каталог AUTOPILOT_COMMERCIAL_DATA_DIR. Выход коллектора задаётся абсолютным COMMERCIAL_OUTPUT вне checkout; файл пишется атомарно с правами 0600. При ошибке вместо прежних чисел сохраняется статус error.

Новое отслеживание подтверждено HTTP-проверкой релиза 4 октября в 08:31:34 UTC. Семидневное окно до этой даты не имеет полного покрытия новых целей: даже измеренный ноль не доказывает отсутствие интереса за всю неделю. Это отмечается measurement.complete=false; processing lag также блокирует конверсии. Доли goal-users/общих users допускаются только при полном покрытии; произвольные соседние этапы воронки не считаются вложенными аудиториями без отдельного подтверждения.

## Идентификатор статьи в CPA-клике

`cpa-click` сохраняет прежнее значение клика. При включённых коммерческих
событиях блок внутри статьи добавляет `contentId` (SHA-256 исходного slug)
и `placement`: inline, article-footer или other. Идентификатор берётся из
серверной разметки ближайшей статьи; адрес страницы, query, заголовок и
данные посетителя не отправляются. Блок вне статьи не получает article id.
Общий делегированный обработчик покрывает inline и нижний блок без дубля.
На localhost CPA-трекинг отключён; сбой счётчика не блокирует переход.

Для расшифровки идентификаторов конкретной сборки:
`node scripts/analytics/content-index.mjs dist`.
Индекс проверяет хеш по реальным собранным страницам, исключает страницы
без article id и отказывает при несовпадении. Сопоставлять старый экспорт
нужно с индексом соответствовавшей ему сборки, включая удалённые статьи.
В Метрике параметры доступны в отчёте «Параметры событий» существующей
JS-цели cpa-click: https://yandex.ru/support/metrica/ru/reports/event-params.

Эти параметры устанавливают источник конкретного клика. Они не связывают
будущую заявку или выплату партнёра с этим материалом автоматически; для
этого нужен поддерживаемый партнёром идентификатор или сверка кабинета.
Приём новых параметров рабочим счётчиком требует реальных наблюдений после
деплоя. История до включения article context остаётся без этого разреза.


## Видимый CTA

`cpa-visible` — минимум половина площади CTA попала в viewport при
активной вкладке. Один сигнал на конкретную кнопку за загрузку страницы;
повторная прокрутка его не дублирует. Фоновая вкладка, невидимая кнопка или
недоступный IntersectionObserver не превращают просмотр страницы в показ.
Возврат из фоновой вкладки запрашивает свежую геометрию. Параметры offer,
contentId и placement используют тот же контролируемый контракт CPA-клика.
Расширение включается только коммерческим флагом и исключено на localhost.

Событие показывает видимость CTA, а не гарантирует чтение рекламы. Сырые
достижения на кнопках нельзя делить на уникальных пользователей и называть
CTR. Для отчёта нужны одинаковые период, единицы, разрез и подтверждённая
полнота; для пользователей используются goal-users. Новая цель требует
read-back регистрации в счётчике 109130279; старые периоды без этого сигнала
остаются без denominator. Подтверждённые заявки и выплаты по-прежнему
берутся из партнёрского кабинета.

Сборщик Reporting API выгружает `cpaVisibleVisitors` и `cpaClickVisitors` через
`goal…users`: это уникальные посетители за окно UTC, а не число событий или
показов отдельных блоков. Для этих двух полей консервативная граница покрытия
— 2026-10-04T21:31:08.779Z, когда публично проверены параметры и видимость.
Отчёт показывает каждую величину и её долю от посетителей сайта. Он не
подставляет их в `offerImpressions` или `ctaCtr`: посетители с кликом пока не
подтверждены как подмножество посетителей с видимым CTA (включая быстрые клики
до callback observer). Неполное окно или задержка API исключают расчёт доли.

## Чтение контекста CPA-событий

`probe-commercial-events.mjs` в том же раннере читает текущие UTC-сутки
через Reporting API. Отдельные отчёты `ym:ep` содержат страницу события
и маргинальные строки параметра contentId; это не страница входа визита.
Счётчик, окно, event-time cutoff, query, точность и вся пагинация проверяются.
Изменение totals между страницами, дубли строк, округление или скрытые данные
оставляют статус ошибки. OAuth и сырые строки API не пишутся в лог/артефакт.

Сохраняются только страницы собственных доменов, совпавшие с опубликованными
slug исходного checkout, и их SHA-256 contentId. Будущие статьи исключены.
Ревизия и размер исходного корпуса записаны в артефакте; этот индекс не
заменяет проверку реального публичного текста. Неизвестные строки учитываются
отдельным числом исключений, их значения не сохраняются. Существующие общие
выгрузки собираются до пробного отчёта и сохраняются также при его отказе.

`events` — число событий, не посетителей, показов уникальным людям или лидов.
Строки contentId нельзя соединять с отдельными строками offer/placement как
параметры одного события. Ноль строк не означает ноль CPA-событий, а ошибка
не превращается в нули. До проверки фактических ответов API
`attributionProven=false`; подтверждённые оплаты, выручка и стоимость остаются
null. Санитизированный `metrika-commercial-event-probe` хранится три дня.

Для read-back журнал раннера содержит производную таблицу чисел событий
по известным публичным slug и покрытие двух отчётов. Идентификаторы и сырые
значения параметров туда не попадают. Совпадение pageEvents и
contentParameterEvents показывает согласованность двух независимых разрезов;
оно не доказывает связь article/offer/placement на уровне одного события.
Отсутствующее значение остаётся null. Таблица ограничена 200 строками,
усечение отмечается отдельно и не считается полным отчётом.
