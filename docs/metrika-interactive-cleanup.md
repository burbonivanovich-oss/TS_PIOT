# Чистка устаревших интерактивных целей Метрики (2026-10-05)

Удаляем из кода и готовим к удалению в Метрике только интерактивный шум.
Коммерческие заявки и реферальные цели не трогаем.

## Что убрано из деклараций

Из `src/data/metrika/goals.json` удалены ровно 7 ID:

- `flagship-ts-piot-completed`, `quiz-ts-piot-completed`,
  `calc-usn-nds-used`, `calc-shtraf-markirovka-used`, `roi-ip-ooo-used`,
  `selector-task`, `selector-result`.

Остались 11 целей без изменений ID и смысла: заявки, CPA,
просмотр и переход к продукту, переход из подбора, начало и попытка
отправки формы, качество визита.

Отправка устаревших событий подавлена централизованно
(`src/utils/obsolete-interactive-goals.mjs` + `src/utils/track.ts`)
и точечно в эмиттерах. Расчёты и экраны интерактивов работают как раньше.
Подавление отправки — не удаление исторических целей.

## Почему обычный sync не подходит

Обычный `sync-goals.mjs` без флагов ничего не удаляет.
`PRUNE=1` для этой задачи запрещён: он снёс бы все orphan-цели разом,
а нужен точный список из 68 ID.

## Порядок (владелец — root)

1. Выкатить код чистки в прод.
2. Снять свежий бэкап целей через Management API GET.
3. Построить readonly-план:
   `node scripts/metrika/remove-obsolete-interactive.mjs --backup <backup.json>`.
4. Сверить счётчик 109130279, 68 target ID, 15 preserve ID,
   hash бэкапа и planHash.
5. Там, где требуется, получить конкретное подтверждение на удаление.
6. Выполнить точное удаление с перепроверкой каждой записи перед DELETE.
7. Снять свежий GET после удаления и убедиться, что 15 сохранённых на месте.

Количество строк в UI доказательством не является.
Без свежего бэкапа, точных ID и подтверждения — результат «заблокировано»,
а не удаление через `PRUNE=1`.

## Проверяемая квитанция удаления (исправление Sol)

HTTP 200 не означает удаление. CLI принимает только JSON объекта с булевым
`success:true`; отказ, пустой/невалидный ответ, ошибка HTTP и противоречивые
поля квитанции останавливают пакет. Helper также отвергает отрицательные или
небулевы флаги, статус ошибки, errors и квитанцию с чужим ID.
`completed` и `receipts` содержат только подтверждённый последовательный
префикс; `failed.remoteId` — первый неподтверждённый ID, `remaining` начинается
с него. Нельзя автоматически повторять DELETE после неопределённого ответа:
операция могла завершиться на сервере. Сначала требуется свежий backend GET
и новый ограниченный план с проверенной идентичностью.

Фактические CLI тесты используют `--import` с полной подменой fetch и mock-only
токеном: никаких реальных запросов API. Исторические 68 кандидатов и 15
защищённых ID счётчика 109130279 не расширяются; это не PRUNE всех orphan.
